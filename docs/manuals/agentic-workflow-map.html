1 · Visão geral do fluxo

Cada agente para em um gate humano. Um agente só grava a aprovação em approvals[] depois que você aprova explicitamente na conversa.

retângulo etapa de agente (cor = agente) tracejado ação humana losango gate humano

Em texto

  1. /tiger cria a demanda e escreve 01-functional-stories.md. Gate: você revisa e aprova.
  2. /turtle exige o graphify dos repositórios, escreve 02-tech-spec.md. Gate: você aprova a spec; só então a branch <type>/<slug> é criada em cada repo afetado.
  3. /termite faz o baseline e o PLAN. Gate: você aprova o plano.
  4. CODE com TDD (um commit Conventional por task), depois VERIFY. Falhou: volta ao TDD na task afetada (máximo 2 retentativas, depois para e reporta). Gate: você aprova o verify.
  5. O Termite pede o graphify manual; você roda e confirma. Status done, a pasta vai para artifacts/archive/ e o status final é archived.

3 · Os agentes

Tiger · produto

Comando
/tiger [slug]
Entradas
A demanda (texto, arquivo ou ticket). Retomada em tiger_in_progress; decisão em tiger_review.
Saídas
  • artifacts/active/<slug>/demand-context.json
  • delivery/01-functional-stories.md (BR, EP/ST/FT, AC em Gherkin, UC, rastreabilidade, Open questions)
Status final: tiger_review.
Skills e templates
Nenhuma skill vendorizada. Usa os templates de knowledge/templates/ (work-rules, functional-history, use-cases, composition).
Modelo por trabalho
Sonnet (sessão): análise, regras, histórias, redação. file-operator (Haiku): pastas, edição e validação do JSON. deep-thinker: análise isolada opcional.
Gate
Revisão do 01-functional-stories.md → approvals[] tiger_review.
Passos
1 intake · 2 regras de negócio · 3 histórias · 4 casos de uso · 5 composição e handoff.

Turtle · arquiteto

Comando
/turtle <slug>
Entradas
Status tiger_review com aprovação registrada; 01-functional-stories.md; graphify-out de cada repo alvo (ausente: para e pede o graphify manual); guides commons + os do demandType; design/ em demandas com front.
Saídas
  • delivery/02-tech-spec.md: Context, Sources, Impact by layer, Sequence diagrams (Mermaid), Work decomposition, Risks, Inferences ([INF-xx])
  • Branch <type>/<slug> em cada repo afetado, registrada em branches[]
Status final: termite_plan.
Skills
Nenhuma skill vendorizada. Graphify primeiro; leitura pontual em repos/ só onde o graphify apontar.
Modelo por trabalho
Sonnet: impacto, spec, inferências. deep-thinker: investigação isolada de leitura. file-operator (Haiku): git (fetch, checkout, pull, criar branch), arquivos, validação.
Gate
Revisão da spec (inferências com “precisa de confirmação” em destaque) → turtle_review. A branch só é criada depois da aprovação.

Termite · developer

Comando
/termite <slug>
Entradas
Status termite_plan com aprovação turtle_review e branches[] preenchido. Retomada em termite_code, termite_verify ou awaiting_graphify.
Saídas
  • delivery/03-implementation-plan.md
  • delivery/04-verification-report.md (comandos reais, matriz AC/BR → teste → tipo → resultado)
  • Um commit Conventional por task, com LEFTHOOK=0
  • Pasta movida para artifacts/archive/
Skills usadas
writing-plans (com overrides: salva em 03-implementation-plan.md, sem handoff), test-driven-development, verification-before-completion. As skills vendorizadas não são editadas.
Testes
  • Unitários sempre: cargo nextest + mockall (backend), Vitest test:unit e test:component (frontend).
  • Integração (testcontainers + Postgres real) só quando a task toca backend + SQL: crates/adapters-postgres/ ou migrations/ (test_scope: unit+integration).
  • Docker é requisito nesses casos (docker info no preflight; sem Docker o Termite para).
Modelo por trabalho
Sonnet: plano, testes e código. file-operator (Haiku): roda comandos, commits, git, docker info, mv, edição do JSON.
Gates
Após o PLAN (termite_plan) · após o VERIFY (termite_verify) · confirmação do graphify. Verify: no máximo 2 retentativas (verifyRetries), depois para e reporta.
Passos
1 preflight · 2 plano · 3 código TDD · 4 verify · 5 graphify e encerramento.

6 · Cheat sheet

Iniciar uma demanda

  1. Clone os repositórios alvo em repos/<nome>/.
  2. Garanta o graphify de cada repo em knowledge/repositories/<nome>/graphify-out/ (o Turtle exige).
  3. Rode /tiger <slug> e descreva a demanda. Se houver UI, coloque prints e links em design/.
  4. Responda à rodada de perguntas do Tiger.

Aprovar um gate

Leia o entregável indicado e responda de forma explícita (por exemplo “aprovado”). O agente grava {stage, approver, date} em approvals[] e avança. Para pedir mudanças, descreva-as: o status não avança.

Em seguida rode o próximo comando: /turtle <slug>, depois /termite <slug>.

Confirmar o graphify

  1. O Termite lista os repositórios alterados e os caminhos de saída.
  2. Rode o graphify manualmente em cada um e grave em knowledge/repositories/<repo>/graphify-out/.
  3. Diga ao Termite que concluiu (com seu nome): ele grava graphify.confirmedBy/At, passa a done e arquiva.

Instalar o RTK

Windows: winget install rtk-ai.rtk. macOS/Linux: brew install rtk. Reinicie o shell e verifique com rtk --version e rtk gain (deve mostrar o painel de economia). Nunca use cargo install rtk do crates.io (outro pacote). Sem o RTK, o hook do projeto não falha: o comando roda normalmente. Não rode rtk init -g.

7 · Divergências e observações encontradas

Estas são diferenças entre as decisões da Fase 2 e o que os SKILL.md/steps realmente fazem hoje. O mapa acima descreve os agentes como estão escritos.

  1. design/ no Termite. A decisão diz que Turtle e Termite leem design/ em demandas de frontend. Os steps do Turtle leem; os do Termite não citam design/ (ele depende da spec).
  2. Skills de frontend sem uso. design-taste-frontend e web-design-guidelines estão instaladas, mas nenhum SKILL.md ou step as referencia.
  3. Integração no Verify. O Verify só roda o perfil integration se alguma task do plano for unit+integration; senão registra “não aplicável”. Docker é exigido apenas quando existem itens de persistência na spec.
  4. Estado created. Não persiste como status atual: o Tiger grava created e tiger_in_progress de uma vez no histórico.
  5. Pré-requisitos de repo. Os perfis do nextest e os scripts test:unit/test:component precisam existir em cada repo; se faltarem, o Termite para e pergunta.
  6. Guides. Foram escritos sem os documentos do time (knowledge/_sources/ ausente); itens [PROPOSED] e o conflito OC-01 (nextest × um container por binário) estão em knowledge/guides/GAPS.md.
